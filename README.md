# xhe

Go implementation of the account hashing used on x-vare.com: **XHEE** for email
addresses and **XHPE** for passwords. Russian version: [README.ru.md](README.ru.md).

The idea is small. The client hashes the email and the password before sending
them, so the server never handles either in plain text. The server then adds a
keyed step of its own before writing to the database.

| protocol | package | protects | client step | server step |
|---|---|---|---|---|
| XHEE | [`xhee`](xhee) | email address | `sha256(lower(trim(email)) + salt)` | `HMAC-SHA256(secret, client hash)` |
| XHPE | [`xhpe`](xhpe) | password | `PBKDF2-SHA256(password, device salt, 100000)` | `bcrypt` over the client hash and a pepper |

The packages are independent; import only the one you need. The other X-HE
modules mentioned on the site (messages, calls) are not part of this repository.

```
xhee/            email protocol
xhpe/            password protocol
internal/        shared input validation
example_test.go  both protocols in one registration/login flow
```

The browser half is `xhe-client.js` on x-vare.com. This package produces the
same bytes, which is checked in the tests against values generated by the Node
code in production.

## Install

```
go get github.com/x-vare/xhe
```

Go 1.24 or newer (the client step uses `crypto/pbkdf2` from the standard library).

## Use

```go
emails, _ := xhee.NewHasher(os.Getenv("XHE_EMAIL_SECRET"), os.Getenv("XHE_EMAIL_SECRET_OLD"))
passwords, _ := xhpe.NewHasher(os.Getenv("XHE_PEPPER"), []string{os.Getenv("XHE_PEPPER_OLD")})

// registration: the client sends emailHash, passwordHash and its salt
storedEmail, _ := emails.Hash(emailHash)
storedPassword, _ := passwords.Hash(passwordHash)

// login
candidates, _ := emails.Candidates(emailHash) // WHERE email_hash IN (...)
res, _ := passwords.Verify(passwordHash, row.PasswordHash)
if res.OK && res.NeedsRehash {
	// right password, but the row uses an old pepper, an old scheme or a low cost:
	// call Hash again and update it
}
```

The client functions (`xhee.ClientHash`, `xhpe.NewSalt`, `xhpe.ClientHash`) are
in the packages too, for tests, CLIs and anything that is not a browser.
A runnable version of the whole flow is in `example_test.go`.

## Rotating secrets

Give the constructors the new secret first and the old ones after it. New rows
use the new secret; lookups and verification also try the old ones.
`xhee.Hasher.Match` reports `legacy` and `xhpe.Hasher.Verify` reports
`NeedsRehash`, so rows can be migrated as people log in, and the old secret can
be dropped once nothing is reported any more.

## Two password schemes (xhpe)

`xhpe.SchemeHMAC` is the default:

```
xhpe2$ + bcrypt(base64(HMAC-SHA256(pepper, clientHash)))
```

`xhpe.SchemeConcat` is what x-vare.com started with, plain `bcrypt(clientHash + pepper)`,
and it has a flaw worth knowing about. bcrypt only reads the first 72 bytes of
its input. A client hash is 64 hex characters, so **only the first 8 bytes of
the pepper influence the result**; the rest is ignored. `TestConcatSchemeMatchesNode` in `xhpe`
shows two different peppers verifying the same row. The scheme is kept so
existing rows can be verified and migrated, not for new deployments.

`Verify` accepts both formats whatever the hasher is configured to write, and
sets `NeedsRehash` for the old one.

## What this does and does not give you

- The server never receives the address or the password. If the database leaks
  without the secrets, neither can be recovered from it.
- An email hash is a lookup key, not anonymity. Anyone holding the database
  **and** the HMAC secret can test guesses against a list of addresses.
- From the server's point of view the client hash *is* the password: whoever
  steals it can send it. The bcrypt step protects the stored copy, not the
  request. TLS and a rate limit on the login endpoint are still required.
- 100,000 PBKDF2 iterations is below the current OWASP figure for PBKDF2-SHA256
  on its own (600,000). Here it is only the client-side stretch in front of
  bcrypt, and the number is fixed by the wire format: changing it means issuing
  new salts.
- No Unicode normalisation is applied to passwords, matching the browser
  client. `strings.ToLower` in Go and `toLowerCase` in JavaScript can disagree
  on a few exotic characters; ordinary addresses are unaffected.
